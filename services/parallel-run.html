Modernisation

The parallel run

How to replace a legacy system without a big-bang rewrite. Pick one seam, build the replacement beside it, then let both process the same work until you can show that the new one is right. The evidence comes before the cutover, not after it.

Prints the one-page summary at the end of this document.

Why the big bang keeps failing

A rewrite promises a clean end state. You build the replacement, you pick a weekend, you switch over. The problem is not the engineering. It is that you cannot prove the new system is correct until it is processing real work, and the moment you cut over you have switched off the only thing that could have told you.

So the first weeks after a big-bang cutover are spent discovering, from customers and from the finance team, the ways in which the new system disagrees with the old one. Every disagreement arrives as an incident. Nobody can say whether the old behaviour was correct, because the old system is off, and the people who understood it have moved on.

The alternative is not to be braver about the cutover. It is to move the proof earlier, so that by the time you switch, the disagreements have already been found, explained, and either fixed or accepted in writing.

The shape of it

03

The replacement goes up behind a clean interface. The legacy keeps running and stays untouched.

04

Both process the same work. Only the legacy output is used. Every difference is classified and explained.

05

Cut over on evidence, switch the legacy piece off for real, and start the next seam with what you learned.

Most of the value is in stage four, and most write-ups skip it. The rest of this document is mainly about stage four.

Picking a seam

A seam is a capability you can lift out with a boundary you can describe. The test is whether you can name what goes in, what comes out, and who is accountable for the result. If you cannot, you have found a region rather than a seam, and you should keep looking.

What makes a good first seam

  • Observable output. It produces something you can compare: a file, a ledger entry, a decision, a number. If the only output is a screen a person looks at, you cannot run this method on it.
  • Enough volume to learn from. You need enough throughput to establish a divergence rate. A process that runs four times a month will take a year to tell you anything.
  • Real pain. Somebody should want this fixed. Modernising a component nobody complains about spends your credibility on nothing.
  • A small blast radius. Few downstream consumers, and ones you can name.
  • An owner who will answer questions. The parallel run generates questions about intended behaviour that only a person can settle.

Seams to avoid first

  • Anything where the output is a side effect you cannot observe, such as a job whose only result is that a downstream system was called.
  • The component with the worst reputation. It is usually the most coupled, and a first attempt that stalls there ends the programme.
  • Anything that has to change functionally at the same time. Replacing the implementation and changing the behaviour together removes your ability to interpret any difference you see. Do one, then the other.
The single most common mistake

Teams pick a seam, then quietly agree to also improve the logic while they are in there. Now every divergence in the parallel run has two possible causes and the comparison tells you nothing. Freeze behaviour for the replacement, prove equivalence, cut over, and only then change what the system does.

Building alongside

The replacement is built behind an interface that describes the seam, not the legacy implementation. Where the legacy cannot be changed, it gets a facade in front of it so that callers talk to the boundary rather than to the old system directly. That facade is what eventually lets you swap which implementation is live without touching any caller.

Before writing the replacement, put a regression harness around the existing behaviour. The harness records real inputs and the outputs the legacy produced for them. It is the thing you will develop against, and it is what turns "we think this is what it does" into a set of cases you can run.

The parallel run

Both implementations receive the same work. The legacy output is the one that is used, and the replacement's output goes to a comparator instead of to the consumer. Nothing downstream changes and nothing is at risk, which is what buys you the freedom to be wrong for a while.

What to compare

Compare the output, not the internals. The replacement is allowed to reach the answer differently, and it usually will. What has to agree is the thing the rest of the business consumes.

Decide the comparison key before you start. For a record-level process it is usually the business identifier plus the fields that matter. For a calculation it is the value and its tolerance. Write this down as a specification rather than leaving it to whoever builds the comparator, because a loose comparison produces a reassuring number that means nothing.

A comparator is a grader

Everything that applies to any other automated check applies here. A comparator that reports a match because both sides produced nothing is worse than no comparator, because it produces a number people trust. Prove it fails before you trust it passing, exactly as described in Harness and verification.

The four outcomes

Every compared pair falls into one of four classes. The classification is the work. A run that reports only "matched" and "did not match" throws away everything useful.

ClassWhat it meansWhat you do
Match Both produced the same result within the agreed tolerance. Count it. Nothing else.
Tolerable divergence They differ in a way that is understood and does not matter, such as ordering, formatting, timestamp precision, or a rounding step that was always arbitrary. Write down the rule that makes it tolerable, then encode that rule in the comparator so it stops appearing. Never dismiss one by hand twice.
Real divergence The replacement is wrong. Fix the replacement, add the case to the regression harness, and keep running. This is the class you expect to dominate early and approach zero.
Legacy defect The replacement is right and the legacy has been wrong, possibly for years. Stop. This one needs a decision from the business, not from engineering. See below.

The awkward case

Class four is the one nobody plans for and it arrives in almost every parallel run of any length. The replacement produces a different answer, you investigate expecting to find a bug, and instead you find that the legacy has been doing something indefensible since before anyone currently employed was there.

The engineering instinct is to make the replacement match, because matching is the goal and the run is nearly over. Doing that silently bakes a known defect into a new system and destroys the honesty of everything else the comparison told you.

The handling is procedural rather than technical:

  1. Quantify it. How many records, over what period, and in which direction. A business owner cannot rule on "sometimes the rounding is off".
  2. Take it to the owner of the outcome, not to the owner of the system. The question is what the answer should be, which is a business question.
  3. Record the ruling in writing, with its date and who made it.
  4. Then implement whichever answer was chosen, and mark the comparator so that this divergence is expected from now on rather than silently equal.
  5. Keep the finding. If the defect had financial or regulatory effect, it is now a disclosed issue with a paper trail, which is a far better position than discovering it after the legacy has been switched off.

Teams find this uncomfortable and then discover it is the most valuable output of the whole exercise. A modernisation that surfaces four long-standing defects and documents the ruling on each has paid for itself before the cutover.

How long to run

Not to a date. Run until the divergence rate on each class of work is low, stable, and explained. Three conditions, and all three have to hold:

  • Real divergences have reached zero and stayed there across a period that includes the cycles this process actually has. If there is a month-end shape to the work, you have not seen the process until you have seen a month end.
  • Every tolerable divergence is encoded as a rule rather than being waved through by a person reading a report.
  • Every legacy defect has a written ruling.

The calendar matters only in that it tells you whether you have seen the rare cases yet. Quarter end, year end, the annual price change, the one customer whose contract predates the system. A parallel run that has not covered a full business cycle has not covered the cases most likely to break after cutover.

Sampling, when full comparison is too expensive

Running everything twice is not always affordable. Where it is not, sample deliberately rather than by convenience:

  • Full comparison on the high-value tail, defined by an actual threshold.
  • A random sample of the rest, at a rate you write down.
  • Deliberate coverage of the known-awkward categories, which are the ones the domain experts will name for you in an afternoon.

Then say in the record that this is what was sampled, because a cutover decision made on a sample is a different claim from one made on the whole population, and the person reading it in two years has a right to know which one they are looking at.

What to keep

The evidence store is the point of the exercise. At minimum, per compared pair: the input reference, both outputs, the class, the rule or ruling that explains it if it was not a match, and when the comparison ran. Aggregated, it gives you the divergence rate over time, which is the chart the cutover decision is actually made on.

Keep it after cutover. It is the only complete account of how the two systems differed, and it is the first thing anyone asks for when a number looks strange six months later.

Deciding to cut over

Cutting over is a decision someone signs, so it should have gates rather than a feeling. These are the ones worth holding.

GateWhat has to be trueBlocking
DivergenceZero real divergences across a period covering a full business cycle, including the rare cases named by the domain owners.Yes
Explained differencesEvery tolerable divergence encoded as a comparator rule. None being dismissed by hand.Yes
Rulings closedEvery legacy defect has a written business ruling, dated and attributed.Yes

The cutover itself should be dull. Flip which implementation the facade routes to. Keep the comparator running for a while with the roles reversed, so the legacy is now the one being observed. That costs almost nothing and it is how you catch the difference that only shows up under real load.

Retiring, for real

The last stage is the one that gets skipped, and skipping it is how an estate ends up with forty systems nobody can switch off. Leaving the legacy running "just in case" means you now operate, patch and licence two systems, and the second one has no owner.

  • Set the switch-off date at cutover, not later. A date that is negotiated afterwards is never reached.
  • Cut its inputs first and watch what breaks. Anything still calling it will announce itself, and it is better to learn that while the system is still running.
  • Archive the data and its schema somewhere readable without the application, since the reason people keep old systems alive is usually the data rather than the code.
  • Then decommission properly: licences, credentials, network access, scheduled jobs, the monitoring that nobody will act on any more.

What this costs

It is not free and it should not be sold as free.

  • You run two implementations for the length of the parallel period, with the compute and the operational attention that implies.
  • You build a comparator and an evidence store, which is real engineering that produces no customer-visible feature.
  • The first cutover is slower to reach than it would have been with a big bang.

What you get back is that the first cutover is the last risky moment rather than the first one, and every seam after it is faster because the harness, the comparator and the facade pattern already exist. Programmes that use this method tend to be slower to the first switch and considerably faster to the last one.

When not to use this

  • No observable output. If the seam produces nothing you can compare, this method has no grip. Find a different boundary or a different approach.
  • A genuine one-shot migration. Moving data from one store to another once is a migration with reconciliation, not a parallel run. The vocabulary overlaps and the method does not.
  • Volume too low to learn from. Below a certain throughput you will never establish a divergence rate, and a designed test suite plus a staged rollout is the better tool.
  • The behaviour has to change immediately. If regulation or a customer commitment means the new behaviour must differ from day one, you cannot prove equivalence because equivalence is not the goal. Handle it as a change programme with its own acceptance criteria.
