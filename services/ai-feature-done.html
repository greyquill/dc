Definition of done for an AI feature

Everyone says AI features ship with evaluation, guardrails and an audit trail. This is what those three words have to mean before a feature reaches a customer, written as gates somebody can actually check.

Why the usual definition of done does not survive contact with a model

A conventional definition of done assumes that a feature which passes its tests today will pass them tomorrow. That assumption holds for deterministic code and it does not hold for a feature whose behaviour depends on a model.

Three things break. The same input can produce different output on two runs, so a single passing test proves less than it used to. The behaviour can change without your code changing, because the model behind it was updated. And the failure mode is usually a plausible wrong answer rather than an error, so nothing alerts.

So the definition of done has to add gates that address those three specifically, and it has to be explicit about which of them block a release.

The gates

1. There is an evaluation set, and it existed before the feature

A set of real inputs with known-correct outputs, written down before the implementation was finished, so it describes the requirement rather than the behaviour of what got built. Thirty well-chosen cases beat three hundred generated ones.

The set has to include, deliberately:

  • The ordinary cases, at the proportion they actually occur.
  • The awkward cases the domain expert can name in an afternoon. Ask them, they always can.
  • Cases where the correct answer is to refuse, or to escalate, or to say it does not know. A feature that has never been tested on an input it should decline will not decline one.

2. It is graded on outputs, and the grader is calibrated

The evaluation asserts on what the feature produced, not on whether it produced something. And the grader itself has been proven to fail a wrong answer, because a grader nobody has tested is a number nobody should trust. The mechanics of this are in Harness and verification.

3. It is run more than once, and the spread is recorded

Non-determinism is a property of the feature, not a nuisance to be argued away. Run each evaluation case several times and record the pass rate and the consistency. A feature that alternates between right and wrong on the same input is not ready even when its average looks acceptable, and the average is exactly what hides it.

4. The guardrails are tested, not just present

Guardrail is a word that gets used for anything from a system prompt line to a hard limit in code. What makes one real is that there is a test proving it holds. For each guardrail:

  • What it prevents, in one sentence.
  • Where it is enforced. A rule stated only in a prompt is a request. A rule enforced in code around the model is a control.
  • A test that attempts the thing and shows it is refused.
The distinction that matters most

Anything you can express only as an instruction to the model is a preference. Anything you can enforce outside the model, in code, is a control. Know which of your guardrails are which, and never describe a preference to a customer as a control.

5. Failure is designed, not incidental

Decide what the feature does when it cannot do its job, and build that path deliberately. What the user sees, whether the work falls back to a person, whether partial output is worse than none. Then test it by making the dependency fail, because the fallback path that has never been exercised is the one that breaks during the incident.

6. Cost and latency are known at peak

Measured per operation, at the volume the feature will actually see rather than the volume it saw in development. Cost per call turns into a monthly number that someone has to approve, and it is much easier to have that conversation before launch.

7. It leaves a record

Enough that somebody who was not there can reconstruct a given output later: the input by reference, the model and version, the decision, any confidence, and whether a person was involved. This is what makes the feature answerable months afterwards, which is when it is always asked about.

8. The conventional bar still applies

Everything an ordinary feature has to clear, it still has to clear. Automated tests on every commit, release gates that block regressions, accessibility, observability. For reference, our own GST Co-Pilot ships with 162 tests and 88 percent coverage, and the AI parts of it did not get an exemption from that.

After launch

The gates above are a photograph. A feature built on a model is a film, because the model can change underneath it without any deployment on your side.

  • Re-run the evaluation set on a schedule, and always before a model version changes. A provider-side update is a new feature, not maintenance.
  • Keep the baseline. The result set from the last accepted release is what every later run is compared against. A case that used to pass and now fails is a regression whatever the average says.
  • Watch the signals the evaluation cannot see. Users retrying, overriding, or abandoning the feature are quality data, and they usually move before the metrics do.
  • Promote real failures into the evaluation set. Anything that went wrong in production becomes a case, so the same fault cannot regress unnoticed twice.
